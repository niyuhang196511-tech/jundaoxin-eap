## 三、保留的 5 个发现（均 MinerU 云端数据流）

`_mineru_cloud`（parsers.py）内 5 个 httpx sink 被标记 SSRF。该函数是 MinerU
批处理 API 的合同实现：**申请上传链接 → 响应返回对象存储 URL → PUT 直传 →
响应返回 batch_id → 轮询/下载均须携带**。即"响应派生数据回流后续请求"是该
第三方 API 的本质流程，无法在不破坏集成的前提下消除数据流。

已就位的补偿控制（本轮新增）：

1. 全部出站 URL 经 `sanitize_url` 校验：仅 http/https、host 非空、拒绝内嵌凭据；
   响应派生的上传/下载 URL 另加 `public_only=True`（IP 字面量须公网、拒绝
   localhost/.local/.internal），并按校验后组件重建（丢弃 fragment 等）。
2. `batch_id` 经 `[A-Za-z0-9_-]{1,128}` 白名单后进入轮询路径。
3. `base_url` 为运营方配置（EAP_MINERU_API_URL），信任模型与连接器 rest 一致。

残余风险：受信但被攻破的第三方 API 可诱导服务端请求其指定公网地址（拒绝内网/
环回后无法触达云元数据与本机服务）；`filename`/`query` 参数仅进入请求体/查询串，
不进入 URL 主机部分。判定：可接受，持续关注 MinerU 侧漏洞通告。
